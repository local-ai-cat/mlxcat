# Tool-calling campaign findings — 2026-08-30

1,344 trials on the M4 Pro (Mac16,7), 8 models × grammar-on/off × t∈{0, 0.7}
× 8 scenarios × non-streaming/streaming × 3 trials, one server process per
campaign (`feat/tool-grammar` @ a721f43), arms differing only by the
per-request `tool_grammar` field. Evidence:
`evidence/2026-08-29-Tim-Apple-M4-ef5db54f.jsonl`; summary table:
`evidence/summary-2026-08-29.md`. Every claim below is recomputable from the
evidence file.

## 1. The grammar lever prices at zero, fleet-wide — in both directions

On every model, grammar-on and grammar-off match within noise on pass rate
AND tok/s (largest tok/s delta ~4% on a 42-trial cell). The 12-prompt A/B's
"costs nothing" conclusion holds at 100x the sample size. But the campaign
also shows it *buys* nothing on these scenarios: not one model's JSON- or
schema-validity moved between arms. Failures are model behavior — wrong
shapes, refusals, loops — which a syntax grammar cannot repair. The lever's
value case remains the long-context tail documented in TOOLGRAMMAR-RESULTS.md
(where unconstrained decoding once collapsed), not average-case validity.
(Qwen3-1.7B's t=0.7 grammar-on cell reads 30/42 vs 35/42 off; two-proportion
at n=42 puts that inside sampling noise — flagged, not concluded.)

## 2. Tool-calling reliability is a MODEL axis, and it now has numbers

t=0, both arms identical, pass rates over 42 trials:

| tier | models | signature |
|---|---|---|
| reliable | Qwen3.5-4B (42/42), Qwen3-Coder-30B (42/42), Qwen3-1.7B (42/42) | full pass including nested schemas, unicode, parallel calls |
| shaped-but-sloppy | gpt-oss-20b (27/42, json 36/36, schema 30/36) | syntax always valid, shapes drift |
| structurally weak | Llama-3.2-3B (27/42), gemma-4-E2B (27/42), Qwen2.5-Coder-7B (24/42), Qwen3.6-27B (30/42) | schema 24/36 — nested arrays string-encoded, required keys dropped |

Llama-3.2-3B additionally: false-calls 3/3 whenever offered a tool it does
not need (every arm, every temperature), and re-calls the tool after
receiving a tool result instead of answering. Its agentic loop failures are
intrinsic, not serving-layer.

## 3. Streaming delta reassembly is clean

Every call-expected cell ran twice, non-streaming and streaming, with the
same validators applied to reassembled `tool_calls` deltas. No
streaming-only failure appeared on any model: the delta encoding path adds
no corruption. (This was an untested claim in TOOLGRAMMAR-RESULTS.md's
out-of-scope list.)

## 4. Thinking models need budget, not grammar

The first 210-trial pass (`…-7a7aaf3d.jsonl`, kept as evidence) failed
Qwen3-1.7B 0/24 on two scenarios with `finish_reason: length` — hundreds of
reasoning tokens before the first tool token starved a 256-token budget in
both arms. At 1024 tokens the same cells pass 42/42 at t=0. At t=0.7
sampling lengthens reasoning further; residual `length` finishes are visible
in the evidence rather than misread as refusals. Any tool-calling harness
(or app timeout) sized for non-thinking models will misdiagnose thinking
models as tool-incapable.

## 5. Controls held

`forced` and `nested_schema` pin `tool_choice` to a named function, which
disarms the grammar by design — those cells are arm-equivalence controls,
and they came back equivalent in every model, which is the expected result
that validates the harness's arm plumbing (one server, per-request field).

## 6. The original failure: located, replayed verbatim, not reproduced (2026-08-30)

The bad chat that started the tool-grammar work was found in the pi session
store (`2026-08-27T14-40-19…` in the mochi-records workspace):
**Qwen3-Coder-30B via the APP's Local API** (`provider: localaicat`, the
legacy parse path) — not via mlxcat — about 100 seconds into a real

|---|---:|---:|---:|---:|---:|

## 7. Verdict on the lever, stated plainly

Across every campaign to date — fleet (1,344), repro (160), long-context
(144), verbatim replay (80): **zero called-but-malformed-JSON calls in
1,500+ emitted calls, in either arm, including on the exact model and the
exact conversation that produced the original failure.** Through mlxcat's
serving path the disease does not occur; the original incident is best
explained by the app's legacy template/parse path, which mlxcat replaced.

What the grammar is, on the evidence: **zero-cost insurance**. It provably
rejects the historical payload (unit-pinned), it prices at zero fleet-wide,
and it has never been observed rescuing a live request. Claims of measured
live benefit should not be made. The measurable tool-calling risks on
current models are elsewhere: thinking/prose budget exhaustion (size
`max_tokens` ≥ 1024, more for 27B-class at t>0) and per-model schema-shape
sloppiness (a model axis — see §2).

Run-condition note: phase-1's Qwen3.6-27B tok/s columns are confounded by a
mid-campaign High Power Mode change on the host; validity columns are
unaffected. Phase-3 32k cells that returned HTTP 507 ran while a second
model was resident (concurrent replay) and are excluded pending a clean
re-run.

## 8. REPRODUCED — the failure is the app harness, and it is alive today

Replaying the same verbatim conversation against the running alpha's Local
API (`:11434`, provider path pi actually uses) instead of mlxcat-http:

| server | settings | trials | exact original failure |
|---|---|---:|---:|
| app Local API :11434 | pi defaults (temp omitted) | 20 | **1** |
| app Local API :11434 | t=0.7 | 20 | **2** |
| mlxcat-http :11702 | both arms × both temps | 80 | 0 |

All three failures are `finish: stop` — not truncation — and the payload is
the 2026-08-27 incident nearly token-for-token: the legacy JSON tool body
with unescaped quotes, leaked to the client as prose because the app's
parser cannot structure it. Evidence:
`evidence/2026-08-30-timapple-m5-badchat-ca150b66.jsonl`.

Interpretation: the serving stack's prompt/template rendering decides which
tool-call format Qwen3-Coder reaches for. mlxcat's rendering elicits the
quote-safe XML-parameter format (0/80); the app's rendering elicits the
fragile JSON body ~5–10% of turns, and its parse path cannot recover it.
The model is constant; the harness is the variable. This is a main-repo
(Local AI Cat) defect, not an mlxcat one — and it is the one live surface
where the tool grammar (or adopting mlxcat's template rendering, likely
cheaper) would deliver a measurable, observed benefit. `feat/tool-grammar`
is unmerged, so the app's embedded engine cannot currently have it.

## 9. Serving-path table — the app harness fails ~46% of agentic tool turns

First standing serving-path correctness campaign: the full scenario suite
against the running alpha's Local API (`--engine-label localai-app`), same
Qwen3-Coder-30B weights mlxcat serves 48/48. App results, 108 trials:

| scenario class | app pass | failure mode |
|---|---|---|
| cold asks (forced/auto/nested/unicode/long/parallel/round-trip/repro) | ~perfect | 1 no_call, 1 bad_schema |
| **agentic_8k (pi-shaped tool history)** | **13/24** | **11 leaked `<tool_call>` blocks** |

Every leak is the same deterministic disease — legacy JSON body, unescaped
quotes, `finish: stop`, including at temperature 0. With prior tool rounds
in context the app's rendering steers the model into the fragile format
~46% of turns (vs 5-10% mid-conversation in §8, and 0% via mlxcat's
rendering). This is why real pi sessions through the app degrade after the
first few tool calls while cold prompts look fine — and why no cold-prompt
benchmark ever caught it. Evidence:
`evidence/2026-08-30-timapple-m5-6446f656.jsonl`.

## 10. Three-way serving showdown (tier 1): mlxcat, the app, LM Studio

Same suite, same Qwen3-Coder-30B 4-bit class (LM Studio's local build —
artifact provenance caveat), 108 trials each:

| server | forced/named tool_choice | auto scenarios | agentic_8k | distinct defect |
|---|---|---|---|---|
| mlxcat-http | full pass | full pass | 48/48 | none observed |
| app Local API | pass | pass | **13/24** | leaks legacy JSON body w/ raw quotes |
| LM Studio | **HTTP 400 — unsupported** | near-pass | 23/24, 0 leaks | occasional empty `arguments` at t>0 |

Each stack fails differently, and none of it is the model: mlxcat is the
only one of the three that serves the full tool-calling surface cleanly.
Named tool_choice is an API capability LM Studio lacks outright (48 of its
53 failures). The app's defect is the §8/§9 rendering leak. Evidence:
`evidence/2026-08-30-timapple-m5-6446f656.jsonl` (both attach campaigns).

## 11. On-device (iPhone) tool-call correctness — first measured rows

`DeviceToolCallTests` booted the real `OpenAIServer` inside the BenchHost
app on the iPhone 16 Pro Max (iPhone17,2) and ran the same suite:
Qwen3-1.7B, 54 trials — **50/54 pass**. Three failures are the Mac-known
thinking-budget class (`length` at t=0.7). The fourth is the find of the
run: the **first malformed-JSON tool call ever observed through mlxcat's
serving path** (~2,100 trials to date) — nested_schema at t=0.7, the
model wrote bracket-confused JSON (`"steps": [["action": …]]`), the
parser correctly refused it, and the call leaked as text with
`finish: stop`. Same disease class as the original app bug, different
syntax error. Scope note: that cell pins a named `tool_choice`, which
disarms the grammar BY DESIGN — the one real malformed emission caught
through mlxcat landed in a cell the grammar deliberately does not cover.
`pi_find_repro` 6/6. mlxcat's serving path is clean
on iOS as measured, not assumed. Evidence:
`evidence/2026-08-30-iPhone17-2-toolcalls-qwen3-1.7b.jsonl`. (The 4B leg
died to a since-fixed harness teardown bug — fa9a70c — and reruns with
the 16k tier tonight.)
